# MAK Marketplace Guide

MAK Marketplace (HeiCode Market) discovers, acquires, and delivers reusable AI capabilities. Marketplace owns listings, orders, entitlements, and the balance ledger. HeiCode Manager (HM) owns identity, organization policy, approval, and deployment. Agent Management (AM) and Swarm own installation, loading, invocation, and runtime health.

This page reflects implementation status on **August 5, 2026**. When the UI differs, trust the entries visible to the current account and the server-returned status.

## Availability

| Capability | Status | Notes |
|---|---|---|
| Browse and filter Skills/MCP | Available | Anonymous users can view the published catalog and details |
| HM sign-in | Available | Acquisition, checkout, and workspace actions require an HM session |
| Free acquisition | Available | Creates an order and active entitlement without external payment |
| Balance purchase | Controlled beta | Existing balance can be atomically debited; real top-up is not open |
| Skill deployment | Controlled beta | Entitlement, governance, deployment, and runtime dispatch exist; accept only with `running` plus runtime evidence |
| Credential-free MCP | Controlled beta | Organization binding and secure AM materialization exist; full production cross-repo E2E is still being accepted |
| Credential-bearing MCP | Not open | Remains fail-closed until runtime secret aliases and short-lived credential leases are complete |
| Real payment/refund/chargeback | Not open | The balance slice is not a complete payment system |
| Versioned publishing/review/emergency revoke | In progress | A publishing route does not mean the full lifecycle is open |
| Publisher settlement/withdrawal | Not open | Revenue sharing, settlement, and reconciliation are incomplete |
| Agent template trading | Not open | Current product kinds are Skill and MCP only |

## Capability kinds

| Kind | Purpose | Delivery |
|---|---|---|
| **Skill** | Reusable methods, knowledge, and workflows | Digest-pinned skill content delivered after entitlement and policy checks |
| **MCP** | External tools such as search, databases, browsers, and knowledge bases | Credential-free claims; organization connection settings and secrets are governed separately by HM |

MCP products never expose customer tokens, passwords, or connection settings in public details, entitlement lists, or ordinary deployment payloads. A credential-bearing MCP without the safe lease path remains `binding_required`; it does not fall back to plaintext or manual pre-provisioning.

## Sign-in and account scope

Marketplace does not maintain a second identity system. Sign-in redirects to HM and then returns to Marketplace. Never place an HM token in a URL.

HM determines whether the session represents an individual or an enterprise member. Enterprise users may choose a personal or organization purchase scope, but the server always revalidates membership, policy permissions, approval, and connector bindings. Selecting an organization in the UI never grants administrative rights.

## Acquire a free capability

1. Open [MAK Marketplace](https://marketplace.heicode.cc/) and find a capability.
2. Review its kind, version, risk, governance key, supported runtimes, delivery mode, and approval requirement.
3. Select **Sign in to acquire** and complete HM sign-in.
4. For enterprise accounts, choose personal or organization scope.
5. Select **Free · Acquire now**.
6. Open **Purchased & authorized** and confirm the entitlement is `active`.

Checkout is idempotent. An order records the transaction; an entitlement records whether the capability can currently be used.

## Purchase with balance

Balance checkout is for accounts or organizations that already have usable balance. A successful operation atomically validates and debits the balance, appends an immutable ledger entry, marks the order paid, and grants exactly one entitlement.

There is currently no public real top-up, card, or third-party payment flow and no complete refund/chargeback workflow. The test-credit endpoint is disabled in production and is not a product recharge feature.

## Deploy to Sub Agent or Swarm

After acquiring an active entitlement:

1. Select **Deploy capability** on the listing detail page.
2. Choose **Sub Agent (single Agent)** or **Swarm**.
3. Confirm the HM organization ID and enter a real target ID.
4. Review the governance key, delivery mode, and entitlement.
5. Create the deployment and follow the returned state.

```text
Order/free acquisition
  -> Marketplace entitlement and Capability Claim
  -> HM entitlement, permission, and policy revalidation
  -> HM Deployment and runtime adapter dispatch
  -> AM or Swarm installation and loading
  -> runtime callback: running or failed
  -> disable/revoke prevents later invocation
```

| State | Meaning |
|---|---|
| `binding_required` | Organization connector binding or safe credential delivery is missing |
| `approval_required` | Waiting for organization approval; runtime has not been called |
| `ready` | Governance passed, but runtime dispatch has not completed |
| `dispatching` | HM is dispatching to AM or Swarm |
| `running` | Runtime confirms the capability is active |
| `failed` | Dispatch, installation, or loading failed |
| `revoking` / `revoked` | Capability is being removed or has been removed |

Only `running`, runtime loaded-state evidence, and a real task prove that a capability works.

## Runtime acceptance

For a Skill, run a task that demonstrates its instructions or workflow. For example, a code-review Skill should analyze a real diff for defects, regressions, and missing tests.

For MCP, invoke an actual tool. A public Reader MCP should retrieve a public URL and return its content. Seeing a server name or configuration record is not runtime proof.

Credential-free MCP still requires an active organization binding, policy, audit, and revoke. Credential-bearing MCP remains unavailable until short-lived credential delivery is complete; never put a long-lived secret in a URL, header, environment variable, Git, log, or Agent memory.

## Workspace entries

Depending on the HM account type, the production navigation can include managed Skills/MCP, publishing, favorites, purchased entitlements, organization governance, balance and ledger, and orders.

Publisher revenue, verification, API/connectors, and account settings are hidden until their backend workflows are complete. A routable page is not proof that a product feature is open. Favorites may explicitly report that the backend is not implemented.

## Disable and revoke

A complete revoke must stop the entitlement or organization authorization, HM deployability and installation/deployment, and the AM/Swarm runtime capability. Verify that the runtime no longer reports the item as loaded and that repeating the original task is denied rather than served from cached configuration.

If no revoke entry is available, contact an organization administrator or platform support. Deleting a local file is not a server-side revoke.

## Troubleshooting

- **`marketplace origin is not allowed`**: open Marketplace from `https://marketplace.heicode.cc` and have an administrator verify the HM origin allowlist. Do not switch to a test domain or place a token in the URL.
- **No entitlement after acquisition**: verify that the current HM identity and personal/organization purchase scope match, then inspect the order and `active` entitlement.
- **Deployment remains `ready`**: inspect HM dispatch events, adapter configuration, target ID, and the AM/Swarm callback. `ready` is not running.
- **MCP remains `binding_required`**: verify an active organization binding. Credential-bearing MCP intentionally remains fail-closed in this release.
- **Deployment is `failed`**: collect the deployment ID, target, governance key, timestamp, `last_error`, runtime load failure, and audit event before retrying.

## Security and source-of-truth boundaries

- Marketplace exclusively writes Listing, SKU, Order, Payment, Entitlement, and Ledger data.
- HM exclusively writes organization policy, Installation, Deployment, approval, and deployment audit data.
- AM/Swarm exclusively write actual installation, loading, invocation, and RuntimeHealth data.
- The web application consumes state and is not a source of truth.
- Capability Claims contain no Skill body, MCP credential, customer connection address, payment data, or user token.
- Long-lived MCP secrets stay in the vault and are referenced by `secret_ref`; ordinary responses, logs, and audits must not reveal plaintext.
- Purchase is not authorization, authorization is not deployment, and `ready` is not running.
